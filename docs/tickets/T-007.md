# T-007: Type-check every field read from a ledger file and refuse unknown or leftover keys

Status: open
Milestone: M3
Risk: high
Issue: #28

## Goal

tally reads a ledger file only when every key is one its format defines and every field has the right type. Any other file is refused with a `TallyError` and never rewritten. Today a wrong type ends in a traceback, `"members": "Ana"` is read as three members, and keys tally doesn't read are dropped on the next save (M2 known limits, D-16, D-17).

## Done when

1. A top-level key the format doesn't define is refused, naming the key. v0.1 allows only `members` and `expenses`. Version 2 allows only `version`, `members` and `entries`, so a version 2 file with a leftover `expenses` is refused. Every command (`balances`, `settle-up`, `add-member`, `add-expense`, `settle`) exits 1 with one `error: ` line, no traceback, and the file's bytes and mtime unchanged. Checked by `tests.test_cli::test_unknown_top_level_key_is_refused`.
2. A missing `members` is refused, naming it. So is a missing `expenses` in a file with no `version`, which includes `{}`. Neither is read as empty. Checked by `tests.test_cli::test_missing_members_or_expenses_is_refused`.
3. An entry key the entry's kind doesn't define is refused, naming the entry's position (from 1) and the key. A version 2 expense allows only `kind`, `payer`, `amount`, `participants` and `note`. A settlement allows only `kind`, `payer`, `receiver` and `amount`. A v0.1 expense allows only `payer`, `amount`, `participants` and `note`, so a `kind` in a v0.1 item is refused (D-17). Checked by `tests.test_ledger::test_unknown_entry_keys_are_refused`.
4. A field of the wrong type is refused, naming its position and field and the JSON type found. `members` and `participants` must be lists of strings. `payer`, `receiver` and `note` must be strings. `amount` must be an integer and not `true`/`false`. `"members": "Ana"` is refused, not read as letters, and `"amount": "10"` gives no traceback. Checked by `tests.test_ledger::test_wrong_field_types_are_refused` and `tests.test_cli::test_wrong_field_types_leave_the_file_unchanged`.
5. `tests/test_cli.py::test_v01_expense_kind_comes_from_the_format_not_the_file` keeps its name, and now asserts that its v0.1 items with `kind` and `receiver` are refused, with the file unchanged (D-17). Checked by `tests.test_cli::test_v01_expense_kind_comes_from_the_format_not_the_file`.
6. Every key tally writes is still accepted. The v0.1 fixture loads with its hard-coded balances. A version 2 ledger with expenses (with and without a note) and settlements round-trips through `to_dict` → `from_dict`. Checked by `tests.test_ledger::test_every_key_tally_writes_is_accepted`.
7. Each of conditions 1 to 5 has at least one assertion that compares the whole message (learning 1).
8. The full test command passes: `.venv/bin/python -m pytest -q`.

## Assumptions

- The checks live in `Ledger.from_dict`, before any entry is recorded, so no command can reach `save` (D-14). `cli.load` already turns decode errors into `TallyError`.
- Files tally wrote stay readable. The v0.1 writer (seed commit `6b629d4`) always wrote `members` and `expenses`, and wrote `payer`, `amount`, `participants` and `note` in every expense. The version 2 writer writes only the keys listed in condition 3. `note` stays optional when reading.
- Condition 6 has no natural red: it guards behaviour that exists today. Prove it with a mutation, for example by dropping `note` from the allowed keys (learning 1).
- The exact message wording is the builder's choice, recorded in the decision log. The tests pin whatever it is.
- Sensitive area: the ledger file format. Every condition guards it. Before the PR, run the blast-radius check from the T-006 round-2 verdict: load a random corpus of valid files with both the base reader and the head reader, and compare.
- M3 adds a split-kind key to expenses. That key joins condition 3's list in the M3 ticket that adds it, not here.
