# T-004: Atomic save

Status: done
Milestone: M2
Risk: low
Issue: #16

## Goal

Saving a ledger is atomic: the new content goes to a temp file in the same directory, which is then renamed over the ledger. A failure during save leaves the old file intact.

## Done when

1. When the temp-file write emits half the bytes and then raises `OSError`, the original file's bytes are intact and no temp file is left in the directory. This test must fail against today's `path.write_text`. Checked by `tests/test_save.py::test_failed_save_leaves_the_old_file_intact`. (S-12)
2. A normal save over an existing file writes the full new content, keeps the file's permission bits and leaves no temp file behind; a save to a path with no file creates it. Checked by `tests/test_save.py::test_save_replaces_the_file_and_leaves_no_temp_file`. (S-13)
3. The full test command passes: `.venv/bin/python -m pytest -q`. (S-14)

## Scenarios

Scenarios: S-12, S-13, S-14 (`docs/milestones/M2-design.md`).

## Depends on

None

## Scope

- `src/tally/cli.py`
- `tests/test_save.py`

## Assumptions

- Only `save` in `cli.py` changes: `tempfile.mkstemp(dir=path.parent, prefix=f".{path.name}.")`, write, flush, `os.fsync`, copy the old file's mode if it exists, `os.replace`. On any exception, remove the temp file and re-raise. Version handling stays in `ledger` (T-003).
- An `OSError` during save still ends in a traceback; M2 doesn't add a message for it (D-13).
- Known limits, not covered: saving through a symlink replaces the link; two processes saving at once can lose a write; `os.replace` may not be atomic on some network filesystems.
- Tests live in a new `tests/test_save.py` so this ticket's scope doesn't overlap T-003's, and the two can be built in parallel.
