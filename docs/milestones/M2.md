# M2: Settlements and a versioned file format

Status: done

## Goal

A member can record that they paid another member back, balances update, and the ledger file carries a version number so later milestones can change it safely.

## Exit criteria

1. `tally settle <from> <to> <amount>` records a settlement; `tally balances` reflects it (payer's balance rises, receiver's falls by the amount).
2. Recording every payment listed by `tally settle-up` brings every balance to 0.
3. Files written by this version contain `"version": 2`. A v0.1 file (no version, kept as `tests/fixtures/v0.1.json`) still loads with identical balances, and is written as version 2 on the next save.
4. A file with an unknown future version is rejected with a `TallyError` naming the version; nothing is written.
5. Saving is atomic: the file is written to a temporary file and renamed over the original, so an error during save leaves the old file intact. Checked by a test that makes the write fail.
6. The full test command passes.
7. A malformed ledger file (version 2 without `entries`, `entries` without a version, invalid JSON, a non-object top level, or an entry missing a field) is refused with a `TallyError` and never rewritten (D-14).

## Not in this milestone

- Editing or deleting a settlement (M4).
- A `migrate` command: upgrade happens on save.

## Risks and assumptions

- Worst case: a bug in the upgrade path corrupts a user's file on save. Exit criteria 3 and 5 are the guards.
- Open question for `/plan M2`: whether settlements live in their own list or as a kind of entry beside expenses. Decided: one ordered entries list (D-10, ADR 0003).

## Known limits

Open spec questions from the M2 verdicts, not addressed in M2. Report: the description of the milestone PR (`milestone/M2` into `main`).

Ledger file reading (T-003, T-005, T-006 verdicts):

- A present field of the wrong type ends in a Python traceback (file unchanged): an expense `"amount": "10"`, `"participants": "Ana"`, `"members": [1]`. T-007.
- `"members": "Ana"` is read as the members `A`, `n`, `a`. T-007.
- A version 2 file with `entries` and a leftover `expenses` key loads from `entries`; the next save drops `expenses` silently. T-007 (D-17).
- A v0.1 item with extra keys (`kind`, `receiver`) loads as an expense (D-16) and the extra keys are dropped on save. T-007 (D-17).
- `{}`, and a version 2 file without `members`, load as empty ledgers and are rewritten on the next save. T-007.
- Downgrade: a v0.1 or M1 tally reads a version 2 file as an empty ledger, and its next save erases the entries. Released code can't refuse it; tell users not to mix versions.
- Reading is strict UTF-8 since T-006; a hand-edited file in another encoding is refused with `ledger file is not UTF-8 text`. Files tally wrote are ASCII.

Saving (T-004 verdicts and design):

- The parent directory isn't `fsync`ed after `os.replace`, so the rename may not survive a power loss on some filesystems; no file is ever left partial.
- A read-only ledger (mode `0444`) is still replaced by a save, since a rename needs only write permission on the directory; its mode is kept.
- Only permission bits are copied; the replaced file belongs to whoever saved.
- Saving through a symlink replaces the link with a regular file; two `tally` processes saving at once can lose a write (last rename wins); `os.replace` may not be atomic on some network filesystems.
- A save that fails with `OSError` ends in a traceback (D-13); with a missing parent directory the traceback names the temp file, not the ledger.
- The tests don't tell apart a save that writes the temp file and then also writes in place.

Settlements (T-005 verdict):

- `tally settle Bo Ana -1` says `not an amount: '-1'` (from `parse_amount`), not "must be more than 0".
- `Settlement` isn't exported from `tally/__init__.py`.
