# M1: Settle up

Status: done

## Goal

The group can ask tally for a list of payments that clears every balance, with as few payments as possible, without changing the ledger.

## Exit criteria

1. `tally settle-up` prints one line per payment (`<from>\t<to>\t<amount>`), and applying every listed payment to the current balances brings each member to exactly 0 cents. Checked by a property test over random ledgers and by hand on a sample ledger.
2. For a ledger of at most 12 members with a non-zero balance, the number of payments equals the true minimum (n minus the largest number of disjoint zero-sum groups). Checked against a brute-force oracle on small random ledgers.
3. Above 12 such members, tally uses the greedy method, prints at most n−1 payments, and says on stderr that the result may not be minimal. Checked by a test with 13+ members.
4. Ties are broken deterministically (by member order as first added), so the same ledger always gives the same output. Checked by running the command twice in a test.
5. `tally settle-up` never writes the ledger file: its bytes are unchanged afterwards. Checked by a test.
6. The full test command passes, including the original 21 tests.

## Not in this milestone

- Recording that a payment happened (M2).
- Any change to the ledger file format.
- Letting the user pick the cap or the method.

## Risks and assumptions

- Assumption: the cap for the exact method is 12 members with a non-zero balance (about 3^12 ≈ 531k subset states, well under a second). See ADR 0001.
- Property tests use seeded random loops in plain pytest, not Hypothesis (D-5).
- Risk: the exact method's worst-case run time near the cap on slow machines; exit criterion 2's test should time it.
